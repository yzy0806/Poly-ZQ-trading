# Execution safety and recovery

1. **Scope.** This change unifies order identity, fill accounting, and reconciliation; adds safe halt and bounded shutdown; and isolates simulated and real execution data. It does not change the heartbeat implementation or IBKR account-summary filtering. The strategy remains BUY-only: no automatic flattening, selling, redemption, or position repair is added.

2. **Durable order identity.** A real hedge's signed payload and exchange order hash are committed before POST. Timeouts, lost replies, crashes, 404 lookups, and missing open-order entries cannot release its reservation. Recovery queries the original hash and may retransmit the identical signed payload after a delay. It never signs a different replacement while the earlier outcome is unresolved. A cancellation acknowledgement alone is insufficient: terminal venue status, cumulative matched quantity, and associated trade IDs must agree with the ledger before any remaining quantity can be replaced.

3. **Fill accounting.** Each trade/order pair retains its entire actual quantity and price. Confirmed fills are allocated to the obligation only up to the amount owed; the remainder stays visible as excess exposure and remains in portfolio cost and quantity. MATCHED, MINED, and RETRYING quantities reserve shares while settlement is pending. CONFIRMED credits the obligation; FAILED releases settlement credit only while preserving the raw record and separate order reservation. Contradictory terminal settlement updates remain reserved for manual investigation. Unidentified venue fills remain in the durable event journal and block reconciliation. Trade semantics follow the [Polymarket order lifecycle](https://docs.polymarket.com/concepts/order-lifecycle).

4. **Reconciliation.** All durable batches and obligations participate, including older completed batches whose fills later require attention. The comparison includes IBKR open/completed orders, executions and target-contract inventory, plus Polymarket open orders, full paginated trade history and all configured event-token positions. Unknown orders are not automatically cancelled on the other account/client's behalf. They block new entries and trigger cancellation of this strategy's working ZQ. Missing completion evidence, pending settlement, stale snapshots, or interrupted reads cannot produce CLEAN. `RECONCILIATION_MAX_AGE_SECONDS` is required; the example environment sets it to 60 seconds. A saved clean result cannot authorize entry after another execution-ledger mutation.

5. **Restart.** The process starts disarmed. Before real hedge submission resumes, fresh venue evidence must rule out unexplained inventory, excess, unknown orders and unidentified fills. Known outstanding obligations may then be hedged while new ZQ entries remain blocked. This prevents blindly buying another hedge when an operator placed one while the engine was offline. IBKR open-order absence is not cancellation evidence; recovery requires a matching completion/status callback. Historical data outside the venue's available execution/completion window may require operator reconstruction.

6. **Halt and shutdown.** Emergency halt immediately prevents new ZQ entry and requests cancellation of every working strategy ZQ order, independent of residual profitability or slow hedge requests. It keeps processing late fills and permits the existing capped hedge mandate. Application shutdown does the same while keeping callbacks and hedge workers alive for up to `SHUTDOWN_DRAIN_SECONDS` (required; example value 20). `ENGINE_STOP` records whether reconciliation completed. A deadline, disconnect, or forced termination cannot guarantee cancellation at the venue; unresolved state must be recovered after restart. Keep the drain deadline below the container's 30-second grace period. Network execution operations use `EXECUTION_REQUEST_TIMEOUT_SECONDS` (required; example value 10).

7. **Database transition.** Back up the existing database before adopting this release. The additive schema stores the execution environment and raw venue receipts. A fresh database binds to IBKR mode, account and API client ID, plus Polymarket simulation mode, wallet, configured API owner, host and chain. Identities use fingerprints rather than credential values. Live execution refuses simulated or unsigned records. Switching between simulation and real trading, paper and live IBKR, or account/wallet identities requires a separate database. Credential-owner changes also require deliberate reconciliation rather than automatic relabelling.

8. **Legacy data.** A pre-change database with execution history has no trustworthy provenance and may already contain clipped fills. Execution startup therefore refuses to bless it automatically; `READ_ONLY` remains available for inspection. Preserve the original and reconstruct actual fills, costs, orders and obligations from venue evidence before migration. There is no automatic migration or reconciliation override for this case. For a flat starting point, verify no outstanding strategy orders or inventory at either venue, retain the old database as history, and configure a fresh live ledger. Never empty a database to conceal an unresolved position.

9. **VPS files and backups.** Use distinct paths, for example `sqlite+aiosqlite:////var/lib/zq-arb/paper.sqlite3` and `sqlite+aiosqlite:////var/lib/zq-arb/live.sqlite3`. The default `engine.sqlite3` name is also supported and is bound by the same identity rules. Keep databases directly in `/var/lib/zq-arb`, with one engine writer per ledger. Deploy the updated backup script so each `*.sqlite3` ledger is backed up separately. An older executable does not enforce these invariants even though it can open the additive schema; any rollback involving execution should remain READ_ONLY until reviewed.

10. **Release evidence.** Offline regression tests cover uncertain POST outcomes and identical replay, concurrent routing, cancellation/fill races, raw excess cost, trade lifecycle conflicts and duplicates, unidentified/multiple maker fills, inventory/order discrepancies, stale reads, restart gating, late fills during halt/shutdown, and database identity mismatches. SDK hash fixtures cover EOA and deposit-wallet signature types and acknowledgement checks. These checks do not establish actual broker/CLOB connectivity, VPS behavior, or resolution of the separately reviewed heartbeat issue.

Local validation on 2026-09-10: 255 Python tests passed on Windows/Python 3.13.12, with 85.99% coverage against the existing 85% threshold. Coverage retains the repository's existing exclusions for the IBKR callback bridge, engine runtime, and entrypoint; offline tests still exercise cancellation and shutdown behavior. Ruff and mypy passed. Dashboard lint, all 14 tests, and the production build passed. Docker/Python 3.12 and actual venue/VPS integration remain release checks.
